# Manifest contract

`manifests/` is the machine-readable product of the client-structure catalog.
Files use one of the families below. JSON is UTF-8 with stable formatting;
source citations and raw address strings are data, not disposable comments.

## Naming boundary

Client-side BCS-Y entries preserve source-backed RTTI `Receiver` names.
Opcode-facing prose leads with direction and opcode before any descriptive
packet name.

## Find the right record

Start with `structs.json` for BCS-S structures and `symbols.json` for BCS-Y
symbols. Use `ir_catalog.json` when a consumer needs the generated
client-structure IR. The other files hold derived views, curated inputs or
individual investigations; they are not interchangeable copies.

### Canonical catalogs

`structs.json` and `symbols.json` own the curated structures and symbols.
Write structs through `tools/_structs_io.py` and symbols through
`tools/_symbols_io.py`. Validate them with `tools/validate_catalog.py`.

### Verified datasets

`gam_hash_names.json` resolves retail-observed hashes to names.
`command_slot_context.json` records generated static-command identity, the
partial category join and ordered command-loadout property writes.
The [tools guide](../tools/README.md) owns their producing commands.

### Bridge catalogs

These derived views combine the canonical catalogs with pinned evidence:

- `lua_api_index.json`, receiver and operation maps, and `lua_to_opcode.json`
- `client_class_registry.json`, `receiver_field_writes.json` and
  `lua_apply_chain_firers.json`
- the lobby character-list projection and sanitized correlation fixture
- the Control-class N-API maps

Rebuild them with their commands in the [tools guide](../tools/README.md), then
run catalog validation. Receiver and operation overlays are curated inputs.
Embedded `{bcsId, address}` pairs copy the canonical VA from `symbols.json`.
Do not edit those copies directly; `hygiene_scan.py` A5 checks their drift.

### Enriched bridge catalogs and inputs

`c2s_bridge_skeleton.json` and `data_dependency_catalog.json` are generated
views of explicit curated inputs and local observations. Their inputs are
`c2s_bridge_overlay.json` and `data_dependency_overlay.json`, which own retained
relationships, observations, confidence, citations and evidence summaries.
The C2S input also owns shared outbound findings.

The [curated bridge ownership contract](../tools/README.md#curated-bridge-ownership)
identifies the derived fields, the catalog-specific direct-emission projection,
and the rebuild/check commands. Embedded `{bcsId, address}` pairs have the same
address-drift check as the other bridge catalogs.

### Client-structure IR

`ir_overlay.json` is curated. `ir_catalog.json` is generated by
`tools/build_ir.py`. After an IR input changes, run `python tools/build_ir.py`
and `python tools/validate_ir.py`.

### Retail evidence

`retail_inputs.json` pins the private objects allowed for each check.
`retail_actor_rebuild_check.json` owns the curated expected observations.
Passing records live under `retail_evidence/`.
`tools/verify_retail_actor_rebuild.py` validates temporary observations and
emits the only allowed attestation form.

### Frozen snapshots

Every `manifests/*.json` file absent from `NAMED_CATALOGS` in
`tools/hygiene_scan.py` is a frozen investigation snapshot. Its topic-slug
filename is an identifier, not a description. Do not rename, regenerate or
reorganize snapshots casually. Add a new maintained catalog to that set.

`lua_callsite_context.json` preserves declaration, reference and invocation
observations for the 19 deferred Lua binding names. Regenerate it only with
the explicit local script corpus and
`tools/extractors/build_lua_callsite_context.py`.

### RTTI index

`rtti_vftable_index.json` is the generated vftable-VA index. Rebuild it with
`tools/build_rtti_index.py` from a local `rtti_extraction_OUR.txt` dump. That
ignored dump is regenerated through `tools/extractors/client_pe`.

## Catalog value forms

The catalog validator accepts a scalar address such as `0x00D31490`, a
semicolon-joined multi-VA identity, a contiguous `0xAAAAAAAA..0xBBBBBBBB`
range, or the `0x00000000` placeholder. Fixed offsets and sizes use hex
strings or decimal integer strings; offsets may also be `n/a`, `variable`, or
`element+0xNN`, while sizes may carry logical sentinels, Lua-domain
descriptions, or a leading hex value with explanatory prose. These forms carry
meaning for consumers, so a new form must be added to
`tools/validate_catalog.py` and documented here before the validator accepts
it.

Role-refinement rows use the `evidenceKind` vocabulary `pcap_observed`,
`pcap_unobserved`, or `live_validated`. The last value is reserved for a claim
verified by the retail 1.23b client accepting the behavior in a live session.
Canonical struct and symbol entries that depend on a live check may carry
`needsReverify: true` with the required `reverifyMethod` string.

The two IR schemas and the retail-evidence attestation schema live in
`schemas/`. IR schemas are loaded by `tools/validate_ir.py`; the attestation
schema is loaded by the retail verifier and its normal-CI tests. A schema that
is not loaded by validation does not belong in this repository.

## Structured Lua references

A `symbols.json` entry may own `luaApiRefs`, an ordered list of explicit Lua
references. When present, the list completely determines that symbol's Lua
index entries. An empty list explicitly supplies none. Editing the symbol's
display name or notes does not change the references.

Each reference has exactly these fields:

| Field | Contract |
| --- | --- |
| `luaName` | An underscore-prefixed Lua identifier. |
| `slot` | A nonnegative integer in the referenced vtable's slot namespace. |
| `source` | `name-luaactorimpl`, `name-other`, or `notes`. These retained evidence categories distinguish a LuaActorImpl identity, another vtable's identity, and a prose mention. Explicit storage does not increase confidence. |
| `bindsOpcode` | Boolean eligibility for the slot-based opcode join. Only `name-luaactorimpl` may be true. Eligibility alone does not establish a receiver or wire opcode. |

The pair `(luaName, source)` is unique within one symbol. Address, BCS identity,
confidence, and citations remain owned by that symbol. Preserve its source
locators and the reason for any exclusion in its notes. A `notes` reference is
still a mention, not proof that the symbol fires that callback.

Symbols without `luaApiRefs` retain mention indexing from other vtable names
and prose. A LuaActorImpl callback name requires explicit references before
the index can be built. New binding claims need the usual evidence review;
parsing a name or copying a mention is not a promotion procedure.

`build_lua_to_opcode.py` checks the indexed LuaActorImpl name and slot against
the canonical reference and uses its `bindsOpcode` flag. It joins only the
receiver map's explicit `luaActorImplSlot`; missing receiver slots remain
unresolved. Other-vtable and prose references cannot supply opcode slots.

After editing canonical references, rebuild `lua_api_index.json`, then
`lua_to_opcode.json`, then the IR using the commands in the
[tools guide](../tools/README.md#bridge-build-pipeline). Run the complete
repository checks. `tools/validate_catalog.py` validates reference fields,
and `tools/test_lua_api_refs.py` verifies the prose-independent binding boundary.

## Lobby character-list contract

`lobby_character_list_projection.json` is the canonical offset, projection,
consumer, validation, and evidence-boundary record for lobby s2c `0x000D`.
`lobby_character_list_capture_correlation.json` is its sanitized restricted-
capture fixture. It carries framing and boolean structural observations only;
raw plaintext and private values are excluded. Normal validation checks the
public shape. Restricted reproduction is explicit and local:

```powershell
python tools\verify_lobby_character_list.py --captures-repo C:\path\to\xivl-captures
```
