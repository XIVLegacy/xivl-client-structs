# Client-structure IR

Use this guide to read `manifests/ir_catalog.json` and the two schemas behind
it. It explains the IR's purpose, record shape, and authority boundary. Field
definitions live in `schemas/ir-v1.schema.json`, which describes every
non-obvious member.

## What it is

One versioned intermediate representation of the client-structure catalog,
generated by `tools/build_ir.py`, shaped so a generator can consume it without
re-parsing prose. Downstream generators can use it for C++20 headers, JSON,
and reference documentation.

Four layers:

- **types** - the BCS-S struct catalog, with namespaces classified, sizes and
  offsets parsed into typed values beside their raw strings, and the byte runs
  no field claims made explicit as `unknown-span` members.
- **symbols** - the BCS-Y catalog, with addresses classified.
- **citations** - every distinct `sourceRef` string in either catalog, parsed
  and reverse-indexed.
- **relationships** - which opcode a receiver handles, which opcode an
  operation class emits, and which Lua name reaches either.

## Authority and normalization

`manifests/structs.json` and `manifests/symbols.json` are the authoritative
homes for their facts. The IR is regenerated from them, and a hand edit to it
is a validation failure (`tools/build_ir.py --check`). The hand-maintained companion is
`manifests/ir_overlay.json`, which is the sole home for the two fields no
source catalog records: type alignment and the reading of a derived unknown
span. Each fact has one home.

Confidence and the optional `needsReverify`/`reverifyMethod` pair are copied
verbatim. `tools/validate_ir.py` invariant I5 fails if normalization moves any
of them. The RTTI corroboration flag on a symbol reports whether the recorded
VA appears as a vftable VA in `manifests/rtti_vftable_index.json` and feeds no
other field.

## Reading a record

Every parsed value keeps its original string in `raw`. A size is `exact`,
`annotated` (a byte count followed by evidence prose), `bounded` (only a
lower or upper bound recorded), or one of `variable` / `unknown` / `logical`
where no native byte width applies. Offsets are `exact`, `element-relative`,
`variable`, or `none`. Addresses are `scalar`, `multi`, `range`, or
`placeholder`.

Address promotion has two historical input conventions for `rtti`, `data`,
and `global` entries. A plain PE RVA becomes a canonical VA by adding the
`0x00400000` image base. Some older values store `RVA - 0x00400000`, so they
require a `0x00800000` shift instead. The catalog
stores the canonical VA after promotion, and
`manifests/rtti_vftable_index.json` is the cross-check for RTTI-backed values.
The IR preserves the catalog string and never applies either shift itself.
Function addresses are preserved verbatim and are not covered by the RTTI
cross-check.

An input string the builder does not recognise raises rather than degrading
to "unknown". A new catalog convention has to be taught to `parse_size()`,
`parse_offset()`, or `parse_address()`, which is the point: a flattened value
is an invisible loss, and a build failure is not.

## Unknown spans

For a type with an exact size, the build derives the complement of its
recorded fields and emits one `unknown-span` member per gap. A span asserts
the absence of a field claim, not the presence of padding - that is why the
default annotation is `unmapped` and why calling a span `padding` or
`reserved` requires an evidence-backed overlay entry.

A type gets `layout.status` `partial` when its size is not an exact byte
count, or when a field starts at a known offset with no derivable width
(`varies`, `variable`). Such a field bounds the extent rather than being
skipped over - skipping it would let a span be emitted straight across a
field that does make a claim - so spans stop there and `layout.trailing`
says the rest is unbounded. Invariant I9 fails on any span containing a
declared field offset.

Only an exact size declares an extent. An annotated size such as
`0x60 (base) / 0x64 (ImplArray2D variant)` keeps its leading token in `bytes`
and its full text in `raw`, but claiming every byte is accounted for at 96
would assert something the prose explicitly contradicts.

## Relationships

The relationship layer joins six sources into one edge set: the coverage matrix, the
inbound receiver map, the outbound operation map, the Lua bridge, the c2s
bridge skeleton, and the receiver field-write catalog.

The opcode key is direction-qualified, `s2c:0x00ca` or `c2s:0x00ca`, because
12 hex values appear in both coverage-matrix tables and mean different things
in each.

The opcode set is the **union over all sources, not the matrix**. The matrix
records what packet capture observed - 108 s2c and 23 c2s rows - while the
bridge catalogs name opcodes capture never saw: the receiver map alone names
19 inbound opcodes with no matrix row, and the outbound serverbound gap names
39. An opcode the matrix does cover carries a `matrix` block with its pattern,
catalog status and pcap count. An opcode it does not cover simply has no such
block. This is the layer's main practical gain over reading the matrix directly.

Every edge is restated from a source catalog. None is inferred by matching
names. The layer carries **identity, direction, and symbol attribution** for
each edge. Per-site evidence stays in the source catalogs and is named here so
the boundary is a decision rather than an accident: the c2s skeleton's
candidate Lua APIs (hypotheses, not edges), the operation map's
`confirmedEmissions` and `confirmedReceives`, the operation vtable's
slot-and-role layout (that is the deferred `vtables` dimension), and the
field-write catalog's per-worker read and write sets.

Two receivers can share a name. Identity is (name, vftable address):
`UserDataReceiver` has one row for its 6-slot vftable and another for its
2-slot one, sharing a slot1 function. The build refuses two rows sharing one
identity.

The two sources also use two Lua name spaces. `lua_to_opcode.json` keys on
bare method names (`_setPosition`), the c2s bridge skeleton on qualified
`Class._method` (`CharaBase._setPosition`), and none of the skeleton's names
exists in the bridge's name set (`relationships.summary.luaBindings` in
`manifests/ir_catalog.json`). Skeleton bindings therefore live in their
own `c2sBindings` field rather than being merged into `luaBindings`. Matching
the two spaces is a naming constraint enforced by the separate fields.

Where sources disagree on an opcode's name, all of them are recorded with
their source and `relationships.summary.nameConflicts` in
`manifests/ir_catalog.json` counts the disagreement. Most are a placeholder
against a real name, but `c2s:0x012f` and `c2s:0x0133` are two different real
names for one opcode. Collapsing them would silently pick a winner.

`payloadTypeBindings`, the type-to-opcode edge, is deferred. No catalog
states one: the only available signals are the `<Receiver>Payload` name
convention and 4-hex strings in prose, and prose hex is unsafe as an opcode
(BCS-S-0005's `0x0B1E` and `0x5F72` are property ids, BCS-S-0001's `0x0002` is
a field value). The catalog therefore leaves the dimension explicitly deferred.

## Dimensions

The `dimensions` block declares, per dimension, whether it is populated,
declared-unknown, deferred, or absent. This is part of the contract:
invariant I3 fails if a value appears
in a dimension the block says is empty, so a value cannot appear without
moving its status in the same change.

The current catalog marks `bases`, `vtables`, and `payloadTypeBindings` as
deferred. `alignment` is declared-unknown
because no catalog records it and deriving it from offsets would be inference.

## Unresolved evidence references

The `citations` entries in `manifests/ir_catalog.json` whose `resolution` is
`in-repo-unresolved` name in-repo relative `sourceRefs` that point at local
Ghidra logs and draft documents never committed. The IR
models this as a first-class citation state, `in-repo-unresolved`, and does
not fail on it. Erasing those
references would destroy the record of where a fact came from, and hard-failing
them would make validation unrunnable without adding value: the reference is
still the honest answer to "where did this come from", it just cannot be
followed from this checkout.

The four states are `external-immutable`, `maintainer-record`,
`in-repo-resolved`, and `in-repo-unresolved`. An `external-immutable` citation
is a `repo:path` sibling or reference citation, validated by shape and never
checked against the checkout. Byte identity, where recorded, lives in a
provenance record's sha256. A `maintainer-record` is a label naming a retired
or islanded maintainer record, not a path.
The category vocabulary underneath them belongs to `tools/hygiene_scan.py`,
whose classifier the builder imports rather than reimplements.

Resolved means *tracked*, not present on disk. `tools/ghidra/logs/` is
gitignored, so reading the filesystem would make a generated artifact depend
on whether the author happened to have local decomp logs, and `Path.exists()`
is case-insensitive on Windows and case-sensitive elsewhere. The builder
passes its own tracked-content predicate into the shared classifier. The scan
keeps the filesystem answer, which is the right one for a human looking at a
working tree.

A live path into a sibling checkout or an absolute path is refused outright,
in the overlay as well as the catalogs: hygiene already gates both as defects,
and the IR must not launder one into a citation.

`EV-NNNN` citation ids are an index into one build, assigned over the sorted
distinct reference strings. They are deliberately not a citation surface -
BCS-Y and BCS-S are the stable identifiers other repositories promote against,
and the IR preserves every one of them unrenumbered (invariant I4).

## Gates

```powershell
python tools\build_ir.py --check   # regenerates identically from the inputs
python tools\validate_ir.py        # two schemas plus thirteen invariants
python tools\test_ir_gates.py      # each of those gates, bite-proved
```

`tools/test_ir_gates.py` plants one defect per invariant and requires the named
check to fail, so a successful run is evidence rather than a claim. Its docstring
records the two things it does not prove. `schemas/` is loaded by
`tools/_schema_check.py`, a stdlib interpreter for the draft 2020-12 subset the
schemas use. It raises on any keyword it does not implement, and consults a
real `jsonschema` install as a reported second opinion where one exists.
